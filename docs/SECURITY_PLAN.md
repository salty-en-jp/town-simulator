# 公開にあたっての安全対策メモ（1.0 までにやること）

> 2026年11月8日に、試作版 v0.5 の時点で整理したもの。1.0 の前に、下の「やることリスト」を上から片づける。
> **v0.5.3 で、開発側の「高」と「中」の項目を対策した**（下の表を参照）。残りはオーナーの設定と、ライセンスなど。

## 前提：今の作りで「悪さ」の範囲はかなり狭い

- **サーバーがない**：GitHub Pages の静的なファイルだけで動いている。アカウント・ログイン・ランキング・通信がないので、他人のデータを盗む・サーバーを落とす、といった被害は起きない
- **データは各自の端末の中だけ**：セーブは各自のブラウザの中（IndexedDB）にだけあり、外には送っていない
- **外部への通信がない**：アクセス解析なし。フォントもアプリに同梱しているので、外部サービスにアクセス情報が送られない

## 懸念と対策

### 1. 細工したセーブファイルを渡される（いちばん現実的）

「ファイルから読み込む」と、LINE・AirDrop などでのセーブの共有が、外からデータが入ってくる唯一の入口。

- **今の状態（v0.5 時点で確認）**
  - 駅名・列車名などの名前は、画面に出すときにエスケープ（`esc()`）している。調べた範囲で漏れはなかった
  - お知らせ（トースト・ステータスバー）は `textContent` で出しているので安全
  - **セーブの中身の形を検査していない**（`src/sim/save.ts` の `deserializeWorld` は、版番号以外はそのまま信じている）
  - ID（`data-id="${t.id}"` など）や車両の種類（`car-dot ${c.type}` などの class 名）は、エスケープせずに HTML に入っている。細工したセーブで文字列を仕込まれると、属性に紛れ込んでスクリプトが動く余地がある
  - おかしな値（存在しない車両の種類など）でゲームが止まることもありえる
- **被害**：そのセーブを開いた人のブラウザでスクリプトが動く。見られるのはこのゲームのセーブくらいだが、偽の画面で何かを入力させることは理屈の上ではできる
- **対策（v0.5.3 で実施）**
  - `src/sim/validate.ts`：数値・整数・文字列の長さ・決まった値（車両や産業の種類など）・タイルの範囲・マップの大きさ・配列の長さを全部確かめる。合わなければ「壊れているため読み込めません（場所）」で断る。ID や種類は数・決まった値しか通らないので、HTML に入れても属性に紛れ込まない
  - ファイルは圧縮のまま 10MB まで、広げたあと 30MB まで（途中で読むのをやめる）
  - 名前・依頼の文章などの文字は、これまでどおり表示のときに `esc()`。サムネイルも `data:image/` だけを通す
  - テスト：`tests/security.test.ts`
- **当初の案**
  - 読み込み時に中身を全部検査する（数値は数値か、種類は決まった値か、名前の長さ、ID の範囲、マップの大きさ、配列の長さなど）。合わなければ「壊れたセーブです」で断る
  - ファイルサイズに上限（巨大なファイルでブラウザが固まるのを防ぐ）
  - HTML を組み立てるところで、名前以外の値もすべてエスケープする（または、自動でエスケープするテンプレートの仕組みにする）

### 2. 万一スクリプトが紛れ込んでも動かさない（保険）

- **対策**：`index.html` に CSP（Content Security Policy）の `<meta>` を入れる。目安：
  - `default-src 'self'`、`script-src 'self'`、`connect-src 'self'`、`font-src 'self'`
  - `img-src 'self' data: blob:`（サムネイルが data URL のため）
  - `style-src 'self' 'unsafe-inline'`（インラインの style を使っているため）
  - `worker-src 'self' blob:`（PixiJS が使う可能性がある）
- PixiJS が CSP の下で動くか（`unsafe-eval` が要らないか）を確かめながら入れる
- **v0.5.3 で実施**：`vite.config.ts` で公開版のビルドだけに `<meta>` を入れる（開発サーバーはインラインのスクリプトを使うため）。PixiJS は `import 'pixi.js/unsafe-eval'` で eval なしで動く。同梱フォントの一部が data URL になるので `font-src 'self' data:`。ほかに `object-src 'none'`、`base-uri 'self'`、`form-action 'none'`

### 3. 公開ページが書き換えられる

GitHub のアカウントやリポジトリが乗っ取られると、公開ページを差し替えられる。

- **オーナーの設定（GitHub の画面で）**
  - [ ] GitHub アカウントの 2段階認証
  - [ ] `main` ブランチの保護（強制プッシュ・削除の禁止、プルリクエスト経由のみ）
  - [ ] Dependabot のアラートを有効にする
- **開発側**
  - [x] GitHub Actions で使う外部の部品（`actions/checkout` など）を、コミットの SHA で固定する（v0.5.3）
  - [ ] ワークフローの権限を最小に（今もほぼ最小：`contents: read`、`pages: write`、`id-token: write`）

### 4. 使っている部品（npm パッケージ）に悪いものが混ざる

- **今の状態**：`package-lock.json` で版を固定し、公開の手順では `npm ci` で入れている
- **対策**
  - [x] 公開の手順に `npm audit --omit=dev --audit-level=high`（弱点チェック）を入れる（v0.5.3）
  - [ ] 部品の更新はまとめて確認してから入れる（自動で最新にしない）

### 5. デバッグ用の入口が公開版に残っている

- **今の状態**：`src/main.ts` で `window.__game` と `window.__debug`（コマンド・パネル・シミュレーション）を公開している。自動テスト（Playwright）用
- **影響**：一人用なので「自分のゲームでズルができる」くらい。ただ 1 の攻撃の足がかりになる
- **対策（v0.5.3 で実施）**：開発サーバー（`import.meta.env.DEV`）か、`npm run build:test`（`VITE_TEST_HOOKS=1`）でビルドしたときだけ有効。公開版のビルドには入らない

### 6. その他（優先度は低め）

- **他のサイトの枠（iframe）に埋め込まれる**：ログインや買い物がないので実害は小さい。GitHub Pages ではヘッダーを設定できないので、必要ならスクリプトで「枠の中なら表示しない」ようにする
- **勝手にコピーして別の場所で公開される**：公開リポジトリなので防げない。ライセンス（どう使ってよいか）と公式の URL を README に書いておく
- **プライバシー**：将来アクセス解析などを入れるなら、その時点で説明ページを用意する
- **将来オンライン機能を入れるとき**（ランキング・クラウド保存・街の共有など）：サーバー側での検査、不正な値・スコアへの対策、アクセスの回数制限、認証が必要。ここが一番大きな作業になるので、入れるときに改めて設計する
